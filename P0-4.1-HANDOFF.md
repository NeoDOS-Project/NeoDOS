## Modelo decidido

La regla productiva adoptada es:

```text
ThreadState::Ready normal => exactamente una entrada en la runqueue de su CPU
ThreadState::Running       => ninguna entrada en runqueue
Blocked/Suspended/Terminated => ninguna entrada en runqueue
```

Excepciones explícitas:

- `BOOT_TID` (`0`): thread bootstrap, no se encola como thread Ready normal.
- `IDLE_TID` (`1`): empieza Ready pero es idle especial y no se encola.

`current_tid` debe identificar el único thread `Running` de la CPU actual. El soporte SMP sigue fuera de esta tarea y está incompleto.

## Cambios locales realizados

### F-01: expiración de timeslice

`Scheduler::on_timer_tick()` ahora recibe `current_rsp`. Cuando expira el timeslice:

1. cambia `Running -> Ready`;
2. guarda `current_rsp` en `k.rsp`;
3. encola el thread exactamente una vez, excepto boot/idle.

`timer_handler_inner()` pasa el RSP real a `on_timer_tick()`.

Cuando una ruta de kernel restaura el mismo thread sin cambiar de contexto, elimina la entrada de runqueue antes de volver a `Running`.

### F-02/F-03: creación de threads

`spawn_kthread()` y `add_thread_to_process()` ya no dejan un thread `Ready` fuera de la runqueue.

Ambos insertan primero el thread como `Suspended` y lo pasan por `Scheduler::make_thread_ready()`, reutilizando la primitiva común de transición y enqueue.

`enqueue_to_cpu_run_queue()` rechaza explícitamente `BOOT_TID` e `IDLE_TID`.

### F-04: validator

`validate_runqueue_invariants()` ahora comprueba:

- `current_tid` existe;
- `current_tid` apunta a `Running`;
- el current pertenece a la CPU actual;
- como máximo un `Running` por CPU;
- TID únicos en la tabla de threads;
- entradas de runqueue sin huérfanos;
- TID únicos en todas las runqueues;
- ownership CPU de cada entrada;
- solo threads Ready normales en runqueue;
- Ready normal exactamente una vez;
- no-Ready sin entradas;
- boot/idle fuera de runqueue.

### Aislamiento de tests

`testing::run_all()` ejecuta cada test dentro de `crate::hal::without_interrupts(...)`, porque las fixtures manipulan estructuras CPU-locales y las interrupciones podían contaminar las runqueues entre casos.

Se añadieron fixtures coherentes para `current_tid`/`Running`:

- `set_test_current()`;
- `prepare_test_schedule()`.

Se añadieron regresiones para:

- expiración de timer y reenqueue único;
- `spawn_kthread()`;
- `add_thread_to_process()`;
- `current_tid` inválido.

## Problema actual de boot

Con el cambio F-02/F-03 y antes del guard final de timer, el boot mostró:

- kernel carga correctamente;
- tests kernel pasan `699/699`;
- NeoInit carga y entra en Ring 3;
- posteriormente QEMU termina en triple fault;
- `qemu_output.log` mostró `RSP=0xDEADBEEFCAFEBABE`, el canario de stack;
- el RIP del fallo se mapeó a `netd_entry_wrapper`.

Causa probable identificada:

`spawn_kthread()` ahora pone `netd` en la runqueue. Un timer que interrumpe Ring 3 puede extraer `netd`, cuyo frame es Ring 0. El handler no puede retornar ese frame como si fuera Ring 3.

Se añadió en `idt.rs`:

```text
prepare_timer_return(next)
```

El helper prepara `TSS.RSP0` solo para frames Ring 3. Además, en la rama de timer que interrumpe Ring 3, si el candidato tiene CS Ring 0:

1. lo devuelve a Ready;
2. lo reencola;
3. elimina la entrada del current user;
4. restaura current como Running;
5. conserva `current_rsp`.

La última ejecución de boot posterior a este guard todavía no se ha completado y debe repetirse.
